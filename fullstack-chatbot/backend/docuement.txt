# 1️⃣ Connection pooling (`asyncpg.create_pool`)

## 🔹 Update `db.py`

```python
import asyncpg
import os
from dotenv import load_dotenv

load_dotenv()

DATABASE_URL = os.getenv("DATABASE_URL")

pool: asyncpg.Pool | None = None


async def init_db():
    global pool
    pool = await asyncpg.create_pool(
        DATABASE_URL,
        min_size=1,
        max_size=10
    )


async def close_db():
    global pool
    if pool:
        await pool.close()


async def get_db():
    if not pool:
        raise RuntimeError("Database pool not initialized")
    return pool
```

@app.post("/chat")
async def chat(req: ChatRequest):
    pool = await get_db()

    async with pool.acquire() as conn:
        # 1️⃣ Create conversation if missing
        if not req.conversation_id:
            row = await conn.fetchrow(
                "INSERT INTO conversations DEFAULT VALUES RETURNING id"
            )
            conversation_id = row["id"]
        else:
            conversation_id = req.conversation_id

        # 2️⃣ Save user message
        await conn.execute(
            """
            INSERT INTO messages (conversation_id, role, content)
            VALUES ($1, $2, $3)
            """,
            conversation_id,
            "user",
            req.message
        )

        # 3️⃣ Call Groq
        response = client.chat.completions.create(
            model="llama-3.1-8b-instant",
            messages=[{"role": "user", "content": req.message}],
        )
        reply = response.choices[0].message.content

        # 4️⃣ Save AI reply
        await conn.execute(
            """
            INSERT INTO messages (conversation_id, role, content)
            VALUES ($1, $2, $3)
            """,
            conversation_id,
            "bot",
            reply
        )

    return {
        "reply": reply,
        "conversation_id": conversation_id
    }

## 3️⃣ What PostgreSQL LISTEN / NOTIFY actually do

This is **not WebSockets** — it’s **database-level messaging**.

### LISTEN

> “Hey Postgres, notify me if something happens on channel X”

### NOTIFY

> “Something happened on channel X, here’s the payload”

### Important:

* LISTEN/NOTIFY **do not send data to the browser**
* They notify **your backend**
* They work **inside PostgreSQL**

---

## 4️⃣ How WebSockets + LISTEN/NOTIFY work together

This is the **key architecture**.

### Full real-time pipeline

```
User A (React)
   ↓ WebSocket
FastAPI
   ↓ INSERT message
PostgreSQL
   ↓ NOTIFY "new_message"
FastAPI (LISTEN)
   ↓
Push message via WebSocket
   ↓
User B (React)
```

### In words:

1. A message is saved to PostgreSQL
2. PostgreSQL emits a NOTIFY event
3. FastAPI hears it (LISTEN)
4. FastAPI pushes it to all connected WebSocket clients

This decouples:

* **DB writes**
* **Real-time delivery**
* **Multiple app instances**

## 5️⃣ Where connection pooling fits into this

Very important.

### Without pooling

* LISTEN connection blocks a DB connection forever ❌
* Chat requests compete with listeners ❌

### With pooling

You split responsibilities:

| Pool usage             | Purpose        |
| ---------------------- | -------------- |
| 1 dedicated connection | LISTEN loop    |
| Pool connections       | Normal queries |

So:

* LISTEN uses **one long-lived connection**
* `/chat`, `/messages`, usage checks use pooled connections

This is why **pooling is mandatory** when using LISTEN.
